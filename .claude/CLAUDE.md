# alfard — project context for Claude Code

## What this is
alfard is a secure-by-default local AI agent orchestration framework.
It is intentionally open-source and auditable. Security-conscious users
should be able to read the entire codebase and understand it fully.

## Three pillars — every decision is filtered through these
1. **Secure** — all safety layers are non-negotiable. Never skip or stub
   the sanitizer, approval gate, audit logger, sandbox, or tool registry.
2. **Useful** — MCP integration is first-class. Agents should be able to
   do real work with Gmail, Slack, GitHub, GDrive out of the box.
3. **Optimized and clean** — not artificially small, not over-engineered.
   Every line justifies its existence. If a function is enough, don't use
   a class. If a class holds real state and gets reused, use a class.

## Architecture — one-line per module
- `main.py` — entry point and smoke test
- `setup_alfard.py` — interactive first-run CLI wizard
- `config/alfard.yaml` — runtime config (gitignored, generated by setup)
- `alfard/llm/providers.py` — lookup table of provider metadata
- `alfard/llm/adapters/openai_compat.py` — adapter for OpenRouter, OpenAI, Ollama, LM Studio
- `alfard/llm/adapters/anthropic_adapter.py` — adapter for Anthropic SDK
- `alfard/llm/client.py` — reads config, instantiates correct adapter
- `alfard/tools/registry.py` — tool registration, minimum-permission enforcement
- `alfard/tools/classifier.py` — labels every tool call reversible or irreversible
- `alfard/tools/sanitizer.py` — strips instruction-like content from untrusted tool output
- `alfard/gate/approval.py` — intercepts irreversible actions, waits for human confirm
- `alfard/sandbox/executor.py` — executes tools in isolated subprocess
- `alfard/integrations/mcp_client.py` — MCP protocol client, manages server connections
- `alfard/integrations/credentials.py` — holds OAuth tokens and API keys, never in LLM context
- `alfard/worktree/manager.py` — file ops go to isolated git branch, never touch main
- `alfard/audit/logger.py` — append-only log of every tool call with source and timestamp
- `alfard/orchestrator/orchestrator.py` — ReAct loop, session state, ties everything together
- `alfard/orchestrator/memory.py` — session memory

## Normalised LLM response format
Every adapter's complete() method returns exactly this shape.
Nothing upstream ever touches the raw SDK response.

```python
{
    "content": str | None,       # text response, None if tool call was made
    "tool_calls": list | None,   # [{"name": str, "arguments": dict}] or None
    "raw": <sdk response object> # kept for debugging only
}
```

## Coding conventions
- One responsibility per file — if you need to open two files to make one
  change, the abstraction is probably wrong
- No features beyond the current spec — no streaming, no retry logic, no
  caching unless explicitly asked for
- Exceptions always chain: `raise RuntimeError("context") from exc`
- Type hints on all function signatures
- Module docstring on every file — one or two sentences max
- No commented-out code in final implementations

## Security rules — never violate these
- Every tool call must go through the tool registry — unregistered tools
  are structurally impossible to call, not just discouraged
- Every irreversible tool call must hit the approval gate before executing
- Untrusted content (web pages, files, email bodies) must go through the
  sanitizer before being returned to the LLM context
- Credentials (API keys, OAuth tokens) are never present in LLM context —
  the credentials manager injects them at execution time only
- The audit log path is never registered as a writable tool

## Dependency rules — read before importing anything

Only use packages that are already in pyproject.toml:
  anthropic, openai, python-dotenv, gitpython, pyyaml, mcp, rich, fastapi, uvicorn

Do not add new dependencies without being explicitly asked to.
If a task seems to require a new package, solve it with the standard
library first. Only suggest a new package if the standard library
genuinely cannot do the job.

When using any package, prefer the minimal surface area:
  - Only import what you actually use
  - Never import a package just for a convenience wrapper around
    something the standard library already does
  - Prefer stdlib over third-party for: file I/O, JSON, regex,
    path handling, subprocesses, HTTP (use httpx or urllib, not requests)

Standard library is always preferred for:
  json, pathlib, subprocess, os, re, datetime, hashlib,
  hmac, secrets, tempfile, shutil, logging, asyncio

Security-sensitive operations must use stdlib only:
  - Secret generation → secrets module
  - Hashing → hashlib
  - File permissions → os/pathlib
  - Never use a third-party package for anything touching credentials,
    tokens, or cryptographic operations

  ## Tool function requirements
Tool functions passed to ToolRegistry.register() must be defined in
importable module files — not lambdas, not functions defined in __main__.
This is required by Python's multiprocessing module on macOS and Windows,
which uses spawn (not fork) and must be able to pickle and reimport the
function in the child process.

## In-chat commands spec (build later)
/clear      — clears conversation context, starts fresh
/remember   — saves last exchange to brain.md
/reset      — resets memory.md for this agent
/skills     — lists active skills for current agent
/status     — shows connected integrations and agent info
/help       — lists all available commands
Commands must work identically across all interfaces.
Command registry lives in alfard/commands/ so any interface can import it.
